# 画像建议

> 基于 6/1-8/17 共 480 个会话（459 OpenCode + 21 Claude Code）的行为分析生成。B14（8/17，1 会话，maxlife 修复 + 分页设计 + 索引撤回登记）为最新批次。

## 沟通通俗性（B15 新增）

**观察**: 8/18 会话 AI 用内部规则术语提问（"README/普通文档引用 .opencode 路径的禁令如何处理？"），用户直接"看不懂你说的什么意思"，AI 大白话重讲（"有一条规则说文档不能引用 .opencode 路径，因为以前这些文件不进 Git，别人 clone 下来看不到……"）后用户才选择。同会话用户还要求解释"AGENTS.md 硬规则——§8 流程要求先列清单拍板"的含义——AI 评估类表述（"硬规则化收益不大"）本身也含内部术语。

**建议**: 用户侧——看不懂直接说"看不懂"，AI 会重讲；AI 侧约束已并入 AGENTS.md §7（术语拆解、提问背景、选项日常语言），本条保留用户侧监督习惯。

## 知识管理投入

**观察**: 6/1-7/18 期间 20-30% 的提问与文档组织、目录重构、Q-A 治理相关。B8 修正"纯工程期零文档治理"假设——生产任务本身触发规则文档化（约 30%）。B10 升至约 40%：15 会话中 6+ 含治理成分，出现合并链治理（05+07→05 再并 06、INDEX→README、时区文档三合一、frontmatter 全删）。**B11 维持高位**：4 会话中 1 个纯治理会话（记忆分层机制设计——全局规则承载协同机制、工作区仓库对 Git 透明）。

**建议**: 保留"每个生产批次至少 1 次 Q-A + 1 次规则文档校对"的基线动作。但新增监控：当文档治理占比连续两个批次 ≥35% 时，检查是否出现"治理本身替代了生产"的倾向——合并链式反应（合并后又继续合并）说明治理动作可能过频。

## 学习方向稳定性

**观察**: B2→openGauss, B4→Linux IPC, B5→Redis 持久化, B6/B8→MongoDB→openGauss 迁移（生产驱动）。B10 主题集中在 openGauss 超时排障 + Go HTTP 客户端机制 + 测试方法论，延续了"生产问题驱动 + 舒适区深挖"的模式，无自发方向跳转。

**建议**: 维持既有策略——自发探索新专题前判断是否有至少 3 个可验证的里程碑。B10 证明生产驱动的连续深挖（同一专题多会话）仍是高产出模式。

## 建了又删的循环

**观察**: B3-B5 删除 6 个以上顶层目录。B10 表现为文档级"建了又删"：合并 05/07 后又把 06 并入 05，时区文档三合一后删除单库版本——删除意愿仍高，但对象从目录降级为章节级，影响范围变小。

**建议**: 维持"新专题等一轮会话再决定"规则。文档合并前先确认目标文档的"与其它文档关系"表引用链——每次合并都会产生连锁更新成本（见"文档合并链"条目）。

## Skill 体系维护负担（边界已明确）

**观察**: Skill 体系经历 build→maintain→too complex→simplify 循环。疲劳针对**规则文本维护**，工作流本身被有效使用。B9 疲劳扩展到 OpenSpec 工作流开销（"不包含openspec内容"）。B10 出现两个方向性信号：正向——test-env 目录自包含化（简化外部依赖）、openspec 中文译本（降低阅读门槛）；负向——对 AI 最低满足的防御（担心 AI 只做最少边界用例）可能推动审核规则变重。

**建议**: 继续执行"规则极简 + 工作流复用"，活跃 Skill 不超过 5 个，修改规则时减法优先。（注：此处"活跃"指**经常维护/修改规则的 skill**，非全局 skill 总数——当前全局 skills 24 个中，多数是低频使用的共享工具，不在此限。）**新增**：当出现"担心 AI 糊弄→想加规则"的冲动时，先问"这条规则 AI 是否会以最低满足方式执行？"——若会，规则无用；优先用验收清单（可核查的产物）替代行为规则（不可核查的要求）。

## 并行 subagent 委托的复核风险

**观察**: B6/B8 用户多次派发并行 subagent 做迁移审核，自己主要看汇总报告。subagent 各自标记语义差异点，但最终回归判定依赖 subagent 的读取完整性。

**建议**: 当 subagent 标记"🔴 真实回归"或"行为变更"时，用户亲自至少抽查 1 个原始代码点，验证 subagent 的读取是否完整。

## Comfort zone 内外差异

**观察**: Redis/openGauss 深入至生产级实验，Linux pipe 明确表示"太吃力先跳过"。B10 新增舒适区深入点：Go HTTP 客户端机制（单会话 12 轮链式追问至内核/连接池层）。

**建议**: 对非 comfort zone，设定最小接触目标（至少跑通一个实验、产出一篇笔记）。对 comfort zone 内专题可放心连续深挖——B10 再次证明这是高产出模式。

## 言行一致性

**观察**: B10 中"我目前似乎没有按照这些方法设计测试用例"——用户诚实承认方法论未践行（知道但未用），言行一致的正向证据。无口头宣言与行为冲突的新案例。

**建议**: 维持现状。注意"知道未用"的方法论（如测试设计矩阵）是后续改进的候选区，但不必强制。

## AI 编写的参考文档需驱动级验证

**观察**: B7/B8 中 AI 多次在对照文档、注释、计划中引入语义偏差，用户逐条比对纠正。B10 延续该警觉：7/30 "应该显式说明，避免AI自己猜"（test-env 兼容模式映射）、8/5 "你验证过吗"（分区表约束）。

**建议**: 维持"AI 编写涉及底层驱动/DB 行为语义的文档前，先执行源码/官方文档级验证"。B10 补充：验证要求已扩展到环境配置类文档（兼容模式映射、镜像版本行为差异）——这类文档的"默认值/映射关系"条目必须给出显式出处，不允许 AI 推断。

> **已升格（2026-08-13）**：本条的约束部分已升格为全局 AGENTS.md §7「结论与证据纪律」第 3 条（性能/兼容性断言必须实测并附命令输出），AI 执行不再依赖本条建议；本条保留观察证据与用户侧监督习惯。

## 变更范围控制

**观察**: B8 多次撤回 AI 扩大范围的改动。B9 "只审核业务逻辑层和 repo，更上层不处理"。B10 延续：8/4 "记录吧，但不需要对了，没意义"（拒绝无意义补充）、"方案B，且不需要截断"（明确简化边界）。

**建议**: 维持"派发前写明'本次只改 X，不改 Y'边界清单"。B10 证明用户已内化此习惯（"只测试PG兼容即可""1、RC1列不填 2、不需要 3、不用"），AI 应主动配合：收到此类收窄指令后，后续动作严格按收窄后的范围执行，不再试探性扩大。

## 跨模块迁移的流水线化（B9 新增）

**观察**: B9 中用户按模块顺序推进迁移，每模块复用审核清单，scope 限定指令密集。B10 未直接涉及（无迁移任务），行为未再现，但 scope 收窄行为在 B10 其他场景继续出现（"只测试PG兼容即可"）。

**建议**: 保留 B9 建议。监控项延续：若未来迁移任务中连续 3 个模块出现"撤回 AI 扩大范围"，升级 scope 为硬约束。

## 同题双会话浪费（B10 新增，B11 未改善，B13 复发）

**观察**: 8/3 09:43 存在两个会话（"Go HTTP请求目标不可达"、"Go请求URL不可访问"），首条消息完全相同——同一问题在两个窗口同时提问。同一分析重复执行，浪费 token 与整理成本。**B11 复发**：insert-bench 监控排查横跨 8/6、8/7 两个会话，且 8/6 会话内混合日志/时区/监控/升级/权限多主题，8/7 重新建立上下文续查。**B13 复发加重**：verify 对比主题横跨 4+ 会话（`ses_001a6206` 仅粘贴 37KB 无交互 → `ses_00172bf6` 完整分析 → `ses_000fba` 相邻分析 → `ses_ffd0666d` bypass 逻辑），前两个会话开头粘贴同一份 37KB 输出作上下文重建；"更新 opengauss skill 文档"任务两会话重复且均以 AI 停在分析层收场；Practice 仓库研究结果"找不到了"需 AI 重新定位——同题浪费 + 结果未沉淀双因叠加。

**建议**: 当在一个会话中遇到"这个问题之前好像问过/在哪问的"时，先 `opencode session list` 或搜索历史会话再开新会话。AI 侧：若用户新会话内容与近期会话高度重复，主动提示"该问题在 X 会话已有分析，是否继续？"。跨日续查同一专题时，优先通过既有专题追踪记录续接而非新会话重述。**B13 补充**：研究/分析类产出（验证方案、分析范式、结论数据）当轮即沉淀到可检索位置（tracking/README），"找不到了"说明沉淀滞后于研究动作——沉淀动作与研究动作同批完成，不等会话收尾。

## AI 确认后必须立即执行（B13 新增，面向用户监督）

**观察**: 8/15 verify 会话用户明确指令"更新下 opengauss skill 文档吧"后 AI 两次停在 plan mode 只给计划不执行，用户"我让你执行这个任务，你在做什么？"（两次）→ 情绪爆发"你TM真是个傻B" → 用户自己接管进程操作。同一会话早期用户还要求"先告诉你打算怎么分析，等我同意后，你再进行分析"——计划先行与确认后执行是一体两面，用户确认即执行授权，确认后再拖延=失职。另"先告诉我要做什么"的 AI 主动方案请求亦获用户许可（"你来验证下吧，先告诉我你打算怎么做"）。

**建议**: AI 侧执行纪律——方案拍板前可以列计划征求同意；拍板后不再重复确认、不再停留"建议/计划"层，直接执行到可验证产物。用户侧监督点：确认拍板后若 AI 仍以计划/建议句式回应，属执行延迟，可直接要求"执行"。

## 文档合并链连锁成本（B10 新增）

**观察**: 7/29 合并 05+07（测试设计），随后又把 06 分层测试并入 05；8/5 时区文档三合一。每次合并触发连锁更新：02 单元测试的"与其它文档关系"表、锚点引用（`07-测试设计矩阵.md` 链接）、Q-A 记录中的文件路径全部需要同步修正——合并的动作是即时的，连锁修正成本是滞后的。

**建议**: 执行文档合并前，先 grep 所有引用被合并文档的链接/锚点（`grep -rn "被合并文件名" 目录`），把连锁修正一次性做完再合并。合并动作本身不复杂，复杂的是引用链——把引用修正并入同一任务，避免"合并完再补链"。

## AI 最低满足防御（B10 新增）

**观察**: 7/29 用户明确表达："这个审核标准有点太宽松了，尤其是对于AI来说。强制AI执行的条目，他尚且可能跳过……我担心AI只设计一个边界用例，满足最低要求，就认为完成任务了。"同时承认"制定详细的规则，难度太高"。8/5 "你验证过吗"显示防御性核查延续。

**建议**: 用户侧——用"可核查产物清单"替代"行为期望描述"：要求 AI 交付测试用例时指定可数产物（如"每函数 ≥3 条边界用例，列出边界值清单"），数字可核查，描述不可核查。AI 侧——当用户担心"最低满足"时，主动在交付物中标注覆盖度（如"该函数 3 条边界用例：空/零/超长，对应等价类 X"），让用户无需追问即可验证。

## 生产环境风险操作（B11 新增）

**观察**: 8/6-8/7 用户在两个生产环境直接部署监控脚本、反向升级数据库版本（7.0.0-RC3 → 6.0.5-LTS）、执行权限变更（CREATE USER/GRANT）与 15GB 备份导出。对数据目录复用有兼容性担忧（"担心数据不兼容"），但整体操作呈"想到即做"节奏，缺结构化风险评估；磁盘写满事故（mongodump 15GB）事后才溯源。

**建议**: 生产变更前要求 AI 先列 3 项检查（影响面/回滚路径/验证手段），用户拍板后再执行——与既有"先列清单决策"模式一致，把该模式从文档决策扩展到生产操作决策。

## 记忆机制规则文本膨胀（B11 新增）

**观察**: 8/7 设计记忆分层机制（索引/记忆/追踪/画像四层协同）时，用户自己也在问"这些内容应该每次会话都携带吗"——机制细节写入全局规则后，每次交互都加载，延续 B9/B10"规则变重"诱因，且治理对象从文档扩展到规则体系本身。

**建议**: 记忆机制描述保持"机制级"而非"操作级"——全局规则只写四层分工与流转边界（每次会话读哪些、何时更新），把实现细节（文件格式、模板）下沉到各仓库或示例，避免全局规则随记忆体系演进持续膨胀。

## 决策未配验证条件致反复返工（B12 新增）

**观察**: 迁移中出现成批"上午定、下午拆"：分区方案当天建当天拆、乐观锁三连撤（要求→全撤回→AI 自曝没必要）、超时归属三改（已切模块回改）、规则存放位置一天三反转（tracking→AGENTS.md→config.yaml）、GroupID 指针化建了回滚。共因：拍板时没有验证条件，之后才遇到反证。

**建议**: 对 DDL/方案选型类决策，拍板时顺带写一句"验证条件"（如"列存：待数据量实测再定"）。有条件的决策被推翻时成本低（条件触发即重新评估），无条件的决策被推翻时已产生实施返工。

## 暂存区工作流代价（B12 新增）

**观察**: 3 周开发期全部活在 Git 暂存区，08-07 单一 38k 行提交交付，无 per-module 历史；"忘记使用 openspec 追踪了，帮我建立对应 change"在会话中反复出现 6+ 次。后果：人工审核无法按模块追踪、回滚粒度等于全仓。

**建议**: 按 tranche/模块提交（保留 per-module 历史），交付提交只做汇总。若坚持暂存区工作流，则审核清单必须含"暂存区边界核查"（漏 git add 的契约文件曾两度导致提交即编译失败）。

## 手工步骤脚本化（B12 新增）

**观察**: 手工操作无校验失误成批出现：手动建 DDL 内容错位（P0，生产建表即崩）、手动删除规则条款事后恢复、生产密码明文落升级手册且目录 gitignore 不追踪、二进制手动 mv 混入排障变量、Nacos 端口抄成 27017（Mongo 端口）。

**建议**: 运维类手工步骤尽量脚本化 + 前置校验（check_yaml 模式——文件存在 + 字段非空 + 端口格式，停机窗口前拦截）；生产密码/配置不进文档，进独立受控配置。

## 测试投入被省的三道防线（B12 新增）

**观察**: 用户主动放弃三处测试防线：verify 抽样（AI 明示能拦住 7 处 bson key 错误）、关键路径集成测试（task10 未落地）、mock 补测试（golang/mock 环境问题后放弃）。对应后果：bson key 错误直达生产 ETL、交付后缺陷靠人工多轮审核仍未全抓住（P0×4 + executor ctx + 显示异常）。

**建议**: verify 抽样与关键路径集成测试不放弃——这两项是"测试形态≠生产形态"类缺陷（ctx 参数/存量表升级路径/真实数据分布）的唯一自动防线。mock 类成本高的测试可以放弃，但放弃的防线要显式登记"此风险由人工审核承担"。

## 文档整理先定骨架（B12 新增）

**观察**: 整理类文档 churn 严重：测试规范 7 轮重写、overview 结构 6 轮调整、审核提示词跨 3 会话迭代、当日建当日删（审核记录/KI 表/迁移清单）、规则存放位置三处游移。

**建议**: 整理类任务开工前先输出"文档骨架"（章节树 + 每章目标读者 + 与其他文档的关系），用户拍板骨架后再填充内容。骨架未定的文档不进入正文编写。

## AI 结论未验证标注（B12 新增，面向用户监督）

**观察**: 迁移中 AI 错误结论成批（详见项目 tracking/analysis-migration-collab.md §B1）："疑似 dead filter 从未命中"（906 万文档 88.5% 证伪）、"0 调用方"（漏 grep cmd/）、"ADD COLUMN IF NOT EXISTS 可用"（生产 42601）、"无窄 patch Update"（device 实有 7 个）——共同点是未实测实查的假设以确定性语气输出。

**建议**: 用户侧监督时，凡遇到"是否存在/是否生效/是否兼容"类 AI 断言，问一句"验证过吗"（B10 已有该习惯，B12 证明必要）。
