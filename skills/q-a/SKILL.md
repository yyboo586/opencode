# 会话整理产出

用户 `/q-a` 或 "会话整理" 触发时，从本次会话中提取独立话题，按统一 Q-A 格式蒸馏并写入：

- **knowledge / design / analysis / debug** 类型 → 项目 `./.opencode/tracking/`（项目知识）
- **insight** 类型（用户行为画像）→ 全局 `~/.config/opencode/me/insights/`（跨仓库共享，不入项目）

> **与 update-profile 的关系**: q-a 产生的 `insight-*.md` 是 `update-profile` 技能的预标注输入。q-a 做显微镜（单会话观察），update-profile 做望远镜（跨批次统计）。这不是重复，是管线。详见 `~/.config/opencode/skills/update-profile/SKILL.md` §0b。

## 触发条件

用户表达以下意图时激活：
- `/q-a`
- "会话整理" / "整理会话" / "记录一下" / "帮我整理"

## 工作流

### Step 1：回顾会话，提取 Q-A 对

遍历本次会话，识别所有独立话题——问答、设计讨论、需求分析、排障结论。同时从会话中识别用户行为模式——能力剖面、学习偏好、情绪特征、思维习惯——提取为 `insight` 类型条目。每个独立话题提取为一个 Q-A 条目。

### Step 2：过滤与压缩

**0. 自包含原则**

每条 Q-A 必须剥离会话上下文，未来读者拿到这条记录能独立理解，不依赖当前对话。但剥离上下文 ≠ 删除上下文——应该是"重新叙述为独立段落"，而非"删除所有背景后留下孤立的结论"。

按以下原则处理每条 Q-A：

**1. 压缩保留清单（不可删除）**

以下内容在压缩后**必须保留**：

| 内容 | 说明 | 示例 |
|------|------|------|
| **WHY** | 决策理由、选择依据 | "选 A 而非 B 是因为 Mongo 行为一致" |
| **源句锚点** | 每条 Q-A 至少 1 处原文引用（用引号标注），作为可验证的锚 | 用户说："我不打算一次性搭建好所谓的基础设施" |
| **边界条件** | 结论的适用范围和前提 | "仅在 openGauss 7.0+ 成立"、"仅适用于单节点" |

**2. 压缩可删除清单（可安全删除）**

| 内容 | 说明 |
|------|------|
| 操作步骤 | cd 到哪个目录、打开了哪个文件、读了几次 |
| 迭代历史 | 第 1 版→第 2 版→第 3 版，只留最终结论，除非迭代本身是证据 |
| AI 解释过程 | 留结论和证据，丢弃中间推理过程 |

**3. 过程层例外**

`debug` 和 `insight` 类型的过程层**不可完全丢弃**：

- `debug`: 排查死胡同是诊断证据的一部分。保留关键失败路径及其原因（"试过 X，不生效，因为 Y"），帮助未来排障者避免重复
- `insight`: 行为本身被发现的过程就是证据。保留对话片段作为推断支撑

**4. 合并** — 多个相关问答合并为一个 Q-A

**5. insight 证据强度评估**

不再使用统一的"≥2 处"计数门槛，改用强度分级：

| 强度 | 定义 | 示例 | 最低要求 |
|------|------|------|---------|
| **强** | 用户明确表达了意图/偏好，或行为与宣言一致 | "我不打算一次性搭建"、"直接撤回，不加补丁" | 1 处即可 |
| **中** | 行为隐含了偏好，但无明确口头表达 | 多次选择方案 A 而非 B，但未明说原因 | ≥2 处 |
| **弱** | 单次行为，可能与具体情境有关 | 某次会话中用了表格，未必是偏好 | 不形成 insight，可在备注中标注 |

> **评估流程**: 每条 insight 先判断强度等级，再按等级决定证据门槛。AI 必须在候选列表中标注每条 insight 的强度等级和证据来源。

### Step 2a：压缩后质量门禁

在进入 Step 3 前，AI 必须对每条压缩后的 Q-A 做以下自检：

> **3 个月后自检**: 逐条问自己："如果我 3 个月后读到这一条，我能理解以下三件事吗？"
>
> 1. 这个问题/发现**是什么**？
> 2. **为什么**是这个结论（不是别的结论）？
> 3. 它有什么**前提条件/适用范围**？
>
> 任何一条答"不能" → 回到 Step 2 补充缺失信息，重新压缩。

此步不产生新输出，但**任何未通过自检的条目不得进入 Step 3**。

### Step 3：归纳与分类

提取完所有 Q-A 后，AI 必须对每条 Q-A 做一次整体审视，同时完成**主题归属**和**类型标注**两项工作：

#### A. 主题归属（避免机械"一条一文件"）

1. **主题归属审视**：多个 Q-A 是否属于同一主题的不同侧面？（如概念定义 → 实例分析 → 决策框架；原理 → 方案 → 选型）。如果是，它们必须放入同一文件（用 `---` 分隔符追加），**不允许拆分为多个独立文件**。
2. **关联标注**：如果某条 Q-A 与其他 Q-A 有关联（概念-实例、原理-方案、根因-修复），在该条 A 末尾追加一行 `关联：<其他 Q-A 标题（或文件名+序号）>`，便于跨条目跳转。
3. **合并判定口诀**：如果删除其中一条，读者对剩余条目的理解会不完整（出现"前文未交代的概念""缺少根因直接跳到方案"等情况），则这些 Q-A 应该合并。

#### B. 类型标注

给每条 Q-A 打 `type` 和 `repo`。

以上 5 类为默认推荐分类，应优先匹配。如果某话题明显不属于其中任何一类，AI 可自拟新 type（简短英文单词），并在候选列表中向用户说明归类理由。

| type | 适用场景 | Q 写什么 | A 写什么 |
|------|---------|---------|---------|
| `knowledge` | 概念/协议/语法/操作符解释 | 概念是什么 | 定义 + 核心机制 + 示例 + 对比（如有） |
| `design` | 模块/服务架构设计、关键决策 | 模块怎么设计的 | 架构概要 + 关键决策 + 数据流 + 模块关系 |
| `analysis` | 需求分析、方案选型 | 需求/问题是什么 | 背景 + 方案 + 验收标准 |
| `debug` | 故障排查、bug 修复 | 故障现象 | 根因 + 修复方案 + 验证命令（可复现） |
| `insight` | 用户行为/偏好/思维模式分析 | 观察到的行为模式 | 证据（对话片段）+ 推断（能力/偏好/情绪特征）+ 建议（可选）。**注意：insight 分析必须实事求是，直述客观观察，不考虑用户感受。这些文件是 `update-profile` skill 的输入源，会在定期画像更新时被消费。** |

`repo` 取当前项目仓库名（如 `rbiotserver`）。跨仓库通用知识用 `global`。**insight 类型统一用 `repo: global`**（用户行为跨仓库成立），且 insight 文件写入全局 `~/.config/opencode/me/insights/` 而非项目 tracking。

这一步的目的是让 AI 承担"知识整理者"的角色，而非仅仅是"对话记录器"。Q-A 产出后必须经过主题归纳与类型标注，避免仅做压缩与格式化后直接交付。

### Step 4：生成候选列表

按统一格式产出每条 Q-A，编号展示给用户预览，等待确认。如果多条 Q-A 经 Step 3 判定为同主题，在列表中用 `→ 建议合并到文件：<文件名>` 明确标注合并建议，让用户在预览阶段就能看到分组结果。

### Step 5：确认写入

用户选择要写入的条目后，按类型写入对应位置：

- `type: insight` → `~/.config/opencode/me/insights/`（跨仓库用户画像证据，所有项目共享）
- 其余类型 → `./.opencode/tracking/`（项目知识）

- 文件命名：`<type>-<简短描述>.md`，如 `knowledge-mongodb-push操作符.md`
- 如果同主题文件已存在，**追加**新 Q-A 到文件末尾（`---` 分隔），不覆盖
- 首次写入前确保目标目录存在（全局 `~/.config/opencode/me/insights/`、项目 `./.opencode/tracking/`）

## 输出格式（统一模板）

```markdown
---
type: knowledge
repo: rbiotserver
tags: [mongodb, $push, 数组操作]
date: 2026-07-17
---

# Q: MongoDB $push 操作符是什么意思？

$push 是 MongoDB 更新操作符，用于向数组字段追加元素。

## A: 核心机制

$push 在 `updateOne` / `updateMany` 中使用，向数组字段末尾添加元素。若字段不存在则自动创建数组。

```js
db.devices.updateOne(
  { _id: "sensor-001" },
  { $push: { events: { type: "alert", ts: Date.now() } } }
)
```

| 对比 | $push | $addToSet |
|------|-------|-----------|
| 重复 | 允许重复 | 自动去重 |
| 性能 | 更快 | 需检查元素存在 |

## 要点

- $push 是追加操作，不覆盖已有元素
- 与 $addToSet 的核心区别：是否去重
- rbiotserver 中 devices 集合 events 字段用 $push 追加告警记录
```

## 注意事项

- **层级判断**：全局通用知识 → `repo: global`；与某个仓库强相关 → 标该仓库名
- **文件名**：纯英文小写 + 连字符，30 字以内
- **tags**：3-6 个，用英文关键词（便于跨语言检索）
- **前置确认**：用户说"全部记录"前，必须展示候选列表等确认
- **补充现有文件**：先 `ls ./.opencode/tracking/`（普通类型）或 `ls ~/.config/opencode/me/insights/`（insight 类型）检查是否已有同主题文件，有则追加

## 记录修正

如果后续会话发现已有 tracking 记录存在事实错误、结论过时、或缺失关键信息：

1. 在原文件末尾追加 `### 更正 (YYYY-MM-DD)` 段
2. 说明修正内容、修正原因、涉及的原结论
3. **不直接修改或覆盖原文**——保留原始记录作为历史参考，修正作为追加

> insight 类型记录的修正同样在 `~/.config/opencode/me/insights/` 对应文件末尾追加更正段。
