# 会话整理产出

用户 `/q-a` 或 "会话整理" 触发时，从本次会话中提取独立话题，按统一 Q-A 格式写入：

- **design / analysis / debug** 类型 → 项目 `./.opencode/tracking/`（项目经历记录）

> **定位：经历记录，不是知识蒸馏**。只记录你亲身经历的事——排障过程、设计决策、需求分析。**概念解释类（AI 教的）不记录**：那是 AI 的知识，蒸馏后你依然看不懂，没有回顾价值。记录的价值在于"以后再踩坑/再决策时回头看"，所以必须还原现场，而不是压缩成看不懂的摘要。

> **与 update-profile 的关系**: 本 skill 只负责经历记录，**不产出用户画像**。画像分析由 `update-profile` skill 单独处理（从会话消息流直接提取画像证据）。职责分离：q-a 是显微镜（经历），update-profile 是望远镜（画像）。

## 触发条件

用户表达以下意图时激活：
- `/q-a`
- "会话整理" / "整理会话" / "记录一下" / "帮我整理"

## 工作流

### Step 1：回顾会话，提取经历话题

遍历本次会话，识别所有**亲身经历**话题——排障过程、设计决策、需求分析、方案选型。每个独立话题提取为一个 Q-A 条目。

**不提取**：纯概念问答（"X 是什么"、"X 和 Y 有什么区别"）——那是 AI 教的知识，不是你的经历，记录无回顾价值。

### Step 2：过滤与整理

**0. 可回顾性原则**

每条记录服务于"以后再踩坑/再决策时回头看"——读者是你自己，你要能**还原现场**：当时发生了什么、为什么这样做、结果如何。剥离会话噪声（寒暄、无关分支），但保留事件本身的完整脉络。

按以下原则处理每条 Q-A：

**1. 保留清单（不可删除）**

| 内容 | 说明 | 示例 |
|------|------|------|
| **现场证据** | 现象、日志、报错、验证命令及输出 | "监控 CSV 15:14:44 行 write_bytes 9276"、报错原文 |
| **WHY** | 决策理由、选择依据 | "选 A 而非 B 是因为 Mongo 行为一致" |
| **边界条件** | 结论的适用范围和前提 | "仅在 openGauss 7.0+ 成立"、"仅适用于单节点" |
| **失败路径** | 试过但不生效的方案及原因 | "试过 X，不生效，因为 Y" |

**2. 可删除清单（安全删除）**

| 内容 | 说明 |
|------|------|
| 操作步骤 | cd 到哪个目录、打开了哪个文件、读了几次 |
| 概念解释 | AI 解释原理的过程段——留结论和证据，丢弃中间推理（那是 AI 的知识） |
| 寒暄/噪声 | 与事件无关的对话 |

**3. 合并** — 多个相关问答合并为一个 Q-A

### Step 2a：整理后质量门禁

在进入 Step 3 前，AI 必须对每条整理后的 Q-A 做以下自检：

> **3 个月后自检**: 逐条问自己："如果我 3 个月后读到这一条，我能还原当时的现场吗？"
>
> 1. 这次**经历**是什么（踩了什么坑 / 做了什么决策 / 分析什么问题）？
> 2. **为什么**是这个结论（不是别的结论）？
> 3. 它有什么**前提条件/适用范围**？
>
> 任何一条答"不能" → 回到 Step 2 补充缺失信息，重新整理。

此步不产生新输出，但**任何未通过自检的条目不得进入 Step 3**。

### Step 3：归纳与分类

提取完所有 Q-A 后，AI 必须对每条 Q-A 做一次整体审视，同时完成**主题归属**和**类型标注**两项工作：

#### A. 主题归属（避免机械"一条一文件"）

1. **主题归属审视**：多个 Q-A 是否属于同一主题的不同侧面？（如概念定义 → 实例分析 → 决策框架；原理 → 方案 → 选型）。如果是，它们必须放入同一文件（用 `---` 分隔符追加），**不允许拆分为多个独立文件**。
2. **关联标注**：如果某条 Q-A 与其他 Q-A 有关联（概念-实例、原理-方案、根因-修复），在该条 A 末尾追加一行 `关联：<其他 Q-A 标题（或文件名+序号）>`，便于跨条目跳转。
3. **合并判定口诀**：如果删除其中一条，读者对剩余条目的理解会不完整（出现"前文未交代的概念""缺少根因直接跳到方案"等情况），则这些 Q-A 应该合并。

#### B. 类型标注

给每条 Q-A 打 `type` 和 `repo`。

以上 3 类为默认推荐分类，应优先匹配。如果某话题明显不属于其中任何一类，AI 可自拟新 type（简短英文单词），并在候选列表中向用户说明归类理由。

| type | 适用场景 | Q 写什么 | A 写什么 |
|------|---------|---------|---------|
| `design` | 模块/服务架构设计、关键决策 | 做了什么决策 | 背景 + 关键决策 + 理由 + 后果 |
| `analysis` | 需求分析、方案选型 | 需求/问题是什么 | 背景 + 方案对比 + 选定方案 + 验收结果 |
| `debug` | 故障排查、bug 修复 | 故障现象 | 现场证据 + 根因 + 修复方案 + 验证命令（可复现） |

`repo` 取当前项目仓库名（如 `rbiotserver`）。跨仓库通用经历用 `global`。

这一步的目的是让 AI 承担"经历整理者"的角色，而非仅仅是"对话记录器"。Q-A 产出后必须经过主题归纳与类型标注，避免仅做格式化后直接交付。

### Step 4：生成候选列表

按统一格式产出每条 Q-A，编号展示给用户预览，等待确认。如果多条 Q-A 经 Step 3 判定为同主题，在列表中用 `→ 建议合并到文件：<文件名>` 明确标注合并建议，让用户在预览阶段就能看到分组结果。

### Step 5：确认写入

用户选择要写入的条目后，按类型写入对应位置：

- 所有类型 → `./.opencode/tracking/`（项目知识）

- 文件命名：`<type>-<简短描述>.md`，如 `debug-og-write-timeout.md`
- 如果同主题文件已存在，**追加**新 Q-A 到文件末尾（`---` 分隔），不覆盖
- 首次写入前确保目标目录存在（项目 `./.opencode/tracking/`）

## 输出格式（统一模板）

```markdown
---
type: debug
repo: rbiotserver
tags: [openGauss, 写入超时, checkpoint]
date: 2026-07-17
---

# Q: openGauss 写入超时 cancel 的根因？

## 现场

- 监控 CSV 15:14:44 行：write_bytes 9276、probe 6.3s（基线 60ms 级别）
- pg_log 同时间点 13 条 "canceling statement due to user request"

## A: 根因与修复

mongodump 15GB 全库导出占满共享磁盘 → SSD 触发内部 GC → WAL fsync 排队 → 业务 INSERT 超时被 cancel。

- 修复：监控脚本增加进程写入溯源（iotrace，write_bytes top10）
- 验证：`awk '$2>1000' monitor.csv` 确认高水位与 mongodump 时间线对齐

## 边界

- 仅在共享磁盘 + SSD 场景成立；短促导出（<1 分钟）不触发 GC
- 死胡同：曾怀疑业务自身写入洪峰，被溯源数据排除（宿主 docker 进程 write_bytes 675MB/5s）
```

## 多记录追加写法

同主题文件续写时，在前一条记录末尾加 `---` 分隔线：

```markdown
---
type: design
repo: global
tags: [监控脚本, 架构]
date: 2026-07-18
---

# Q: monitor.sh 如何支持双库探测？

...
```

## 注意事项

- **层级判断**：跨仓库通用经历 → `repo: global`；与某个仓库强相关 → 标该仓库名
- **文件名**：纯英文小写 + 连字符，30 字以内
- **tags**：3-6 个，用英文关键词（便于跨语言检索）
- **前置确认**：用户说"全部记录"前，必须展示候选列表等确认
- **补充现有文件**：先 `ls ./.opencode/tracking/` 检查是否已有同主题文件，有则追加

## 记录修正

如果后续会话发现已有 tracking 记录存在事实错误、结论过时、或缺失关键信息：

1. 在原文件末尾追加 `### 更正 (YYYY-MM-DD)` 段
2. 说明修正内容、修正原因、涉及的原结论
3. **不直接修改或覆盖原文**——保留原始记录作为历史参考，修正作为追加
