# TDD：Go 测试驱动开发工作流

## 触发方式

**手动触发**：`/tdd`

**自动触发**：
- 用户写新的 Go 函数/方法
- 用户给现有代码加测试覆盖
- 用户写 benchmark / fuzz test
- 用户说"测试""写测试""跑测试"时

---

## 核心流程

```
用户要写代码/加测试
        │
        ▼
  Step 1: 写失败测试（RED）— 先写测试，定义期望行为
        │
        ▼
  Step 2: 最小实现（GREEN）— 写最少代码让测试通过
        │
        ▼
  Step 3: 重构（REFACTOR）— 改善代码，测试保持通过
        │
        ▼
  Step 4: 代码审核 — 按检查清单审核
        │
        ▼
  重复 Step 1-4，直到功能完成
```

---

## Step 1: RED — 写失败测试

**规则**：
- 先写测试，不写实现代码
- 测试必须能编译，但运行必须失败
- 测试命名：`Test<功能>_<场景>`，如 `TestAdd_PositiveNumbers`
- 优先用 table-driven tests
- 每个测试只验证一个行为

**AI 职责**：
- 帮用户写测试骨架（func 签名 + table 结构 + t.Run）
- 不写实现代码
- 指出遗漏的边界 case

---

## Step 2: GREEN — 最小实现

**规则**：
- 写最少代码让测试通过——不多不少
- 允许 hardcode（下一步重构会修正）
- 测试通过即可，不考虑优化

**AI 职责**：
- 不直接给实现代码
- 只给操作顺序级提示（如"先处理 nil case，再处理正常情况"）
- 指出为什么卡住（概念层面），不解释怎么写（实现层面）

---

## Step 3: REFACTOR — 重构

**规则**：
- 重构前后测试必须全过
- 每次只做一种重构（提取函数/重命名/消除重复）
- 重构后立即跑测试确认

**常见重构方向**：
- 消除重复代码（3 次以上重复 → 提取辅助函数）
- 减少嵌套（早返回）
- 改善命名（表达意图）
- 预分配容量（已知大小时 `make([]T, 0, n)`）

---

## Step 4: 代码审核

> 所有测试通过后，AI 必须按此清单审核。不直接给修正代码，指出位置 + 引导思考。

### 必查项（不通过则阻塞）

| 项 | 检查内容 |
|----|---------|
| 测试通过 | 所有测试 case 通过 |
| base case 完整 | nil / 空 / 边界值（0、负数、超大输入）都处理 |
| 错误处理 | `err != nil` 时的返回/包装；避免吞错 |

### 应查项（Go 惯用 + 质量）

| 项 | 反模式 | 惯用写法 |
|----|--------|---------|
| 命名 | `data`, `tmp`, `a` | 表达意图：`queue`, `currentLevel` |
| 早返回 | `if cond { ... 大段 ... }` 嵌套 | `if !cond { return }; ...` |
| range vs for i | 不需要索引时用 `for i` | `for _, x := range s` |
| defer | 手动 Close | `defer file.Close()` |
| 全局变量 | 用全局传递状态 | 显式参数传递 |

### 性能（基础优化）

| 项 | 反模式 | 优化 |
|----|--------|------|
| 预分配 | `var s []int; append` | `make([]int, 0, n)` |
| 循环内分配 | 每轮 `make` | 循环外预分配 |
| 值拷贝 | 大结构体按值传 | 按指针传 |
| 字符串拼接 | `s += "x"` | `strings.Builder` |

### 不强求项（学习场景豁免）

- 包结构 / 接口抽象
- 极致性能优化
- 并发安全（除非正在学并发主题）
- 跨包测试覆盖率指标

### 审核输出格式

```
代码审核报告

✅ 必查项：全通过

🟡 应查项（建议改进，非阻塞）：
  1. [行号] 命名：变量 `tmp` 表意不清，建议改为 <引导用户想>
  2. [行号] 早返回：if 嵌套 3 层，可以用 <引导>

🔵 性能（基础优化）：
  3. [行号] 预分配：`var s []int` 后 append 循环，能否预分配？

不强求项：跳过（学习场景豁免）

行动建议：
- 修改 1-3 项后重测
- 不修改也可（功能已通过），但建议至少修第 X 项
```

## 测试模式速查

> 完整代码示例见 [Go测试模式参考.md](../../11-Go/docs/Go测试模式参考.md)

| 模式 | 何时用 | 关键 API |
|------|--------|---------|
| Table-driven | 多场景测试 | `[]struct{name, input, want}` + `t.Run` |
| Subtests | 同功能多场景 | `t.Run("场景", func(t *T))` |
| Benchmark | 性能测试 | `func BenchmarkXxx(b *B)` + `b.ResetTimer()` |
| Fuzz | 输入验证 | `func FuzzXxx(f *F)` + `f.Add` + `f.Fuzz` |
| Golden files | 输出比对 | `testdata/` + `-update` flag |
| Mock | 依赖隔离 | 接口 + 手写 mock struct |
