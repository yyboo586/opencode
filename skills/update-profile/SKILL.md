# update-profile — 开发者画像生成（演进模式）

> 支持 OpenCode CLI 和 Claude Code CLI 两种本地会话源。

## 触发

用户说 `/update-profile` 或 "更新画像"。

可选参数：

| 命令 | 数据源 |
|------|--------|
| `/update-profile` | 仅 OpenCode 会话（默认） |
| `/update-profile --claude` | 仅 Claude Code 会话 |
| `/update-profile --both` | 两种来源合并分析 |

## 设计原则

画像采用**演进模式**而非覆盖重写。支持 OpenCode 和 Claude Code 双源。每次运行：
1. 读取现有画像（`~/.config/opencode/me/profile.md`）作为基线
2. 从指定数据源提取会话（支持 opencode/claude/both）
3. 分析新会话数据，与基线做差量对比
4. 合并增量（保留/深化/追加），永不自动删除已有条目
5. 基于负面信号生成建议到 advice.md
6. 记录演进历史

## 流程

### Step 0: 读取基线画像

**0a. 读取画像基线**

读取现有 `~/.config/opencode/me/profile.md`，输出以下内容供后续步骤使用：

- 所有现有的分类标题（如 `## 编码风格`）
- 每个条目下的具体描述
- 尾部是否已有 `演进记录` 段

写入 `profile.md` 时将用到这些基线信息。

> **画像证据来源**: 本 skill 是画像分析的唯一入口（q-a 只做知识蒸馏，不产出画像）。画像证据直接来自 Step 2 提取的会话消息流，无预标注输入。历史若有遗留 insight 资产，按 `## 待观察` 段的批次标注追溯来源即可。

### Step 1: 确定数据源

**1a. 确定数据来源**

根据用户指令决定分析哪个 CLI 的会话：仅 opencode（默认）、仅 claude、或 both。

**1b. 确定时间范围**

OpenCode 会话列表:
```bash
opencode session list
```

Claude Code 会话列表（直接读文件）:
```bash
ls ~/.claude/projects/<project-slug>/*.jsonl
```

其中 `<project-slug>` 是将项目绝对路径中的 `/` 替换为 `-`，并在开头加 `-`。如 `/mnt/d/platform/Practice` → `-mnt-d-platform-Practice`。

评估数据量后，从以下两种模式中选择并告知用户理由：
- **全量**：所有会话逐批分析。数据量可控（总原始内容 < 上下文窗口）时选用。
- **最近一周**：数据量过大或只需反映最新习惯时选用。

### Step 2: 提取会话数据

**2a. OpenCode 会话导出**

```bash
opencode export <session_id> > /tmp/session_<id>.json
```

导出后需去除第一行（"Exporting session: ..."），剩余为 JSON。

**2b. Claude Code 会话读取**

Claude Code 没有导出命令，直接读取 `~/.claude/projects/<project-slug>/*.jsonl` 文件。

文件名格式: `<uuid>.jsonl`，每个文件是一个会话。

JSONL 解析规则:

```python
for line in file:
    d = json.loads(line.strip())
    t = d.get('type')
    if t == 'user':
        # 用户消息
        msg = d.get('message', {})
        content = msg.get('content', [])  # list of {type: "text", text: "..."}
        text = ' '.join(c['text'] for c in content if c.get('type') == 'text')
        role = 'user'
    elif t == 'assistant':
        # AI 消息
        msg = d.get('message', {})
        content = msg.get('content', [])
        text = ' '.join(c['text'] for c in content if c.get('type') == 'text')
        role = 'assistant'
    elif t == 'ai-title':
        # 会话标题
        title = d.get('aiTitle', '')
    else:
        continue  # 跳过 mode/permission/file-history-snapshot 等
```

关键字段:
- `type`: `"user"` / `"assistant"` / `"ai-title"`
- `message.content`: `[{type: "text", text: "..."}, ...]`
- `timestamp`: ISO 8601 字符串（如 `"2026-06-30T01:02:43.661Z"`），不是 Unix 毫秒。部分非消息行（mode/permission 等）无 timestamp
- `cwd`: 工作目录

**2c. 统一消息流**

两种来源的消息统一为以下中间格式，后续分析步骤对此无感知:

```json
[{"role": "user", "text": "...", "timestamp_epoch": 1720000000, "session_title": "..."}]
```

时间戳统一为 epoch 秒:
- OpenCode: `msg.info.time.created / 1000`
- Claude Code: `datetime.fromisoformat(d.timestamp.replace('Z', '+00:00')).timestamp()`

**2d. 日期筛选**

从统一消息流中按用户指定的日期范围筛选。只保留有实质性技术讨论的会话（≥3 轮用户提问且非问候/天气）。

### Step 3: 对比分析

对 Step 2 中提取的统一消息流进行分析（与基线对照，而非从零开始）。关注维度（不限于）：

- 编码风格：语言、错误处理、架构品味、命名习惯、测试风格
- 沟通偏好：简洁度、格式偏好、交互模式
- 思维模式：推理路径、强弱项、学习方式
- 技术广度：语言、工具、范式偏好

分析产出分三类：

| 类型 | 定义 | 处理 |
|------|------|------|
| **深化** | 基线中已有条目，新数据提供了更强的证据或量化支撑 | 保留原措辞，补充新证据/数据 |
| **新增** | 基线中不存在的新发现 | 追加为独立条目或子项，标注 `[新: batch]` |
| **未触及** | 基线中有但本轮数据未覆盖 | **保留不变**，不自动衰退或删除 |

### 冲突处理（关键原则）

"矛盾"本质上分三种情况，不应一刀切：

| 实际场景 | 示例 | 处理 |
|---------|------|------|
| **演进**（能力提升/习惯变化） | 基线："Go 测试初学者" → B2："写复杂 benchmark 套件" | 更新原条目描述，标注 `[B2: 演进]`。保留演进轨迹历史到演进记录段。 |
| **上下文补充**（两个行为并存于不同场景） | 基线："问题精炼不要铺垫" → B2 出现"长篇背景描述" | 两者都是真的——前者是沟通风格，后者是场景需要。追加限定语，标注 `[B2: 补充]`。 |
| **真实矛盾**（新旧之间不可调和） | 基线："永不写注释" → B2："要求加注释解释复杂度" | 保留旧条目+追加新条目并行存在，顶部标注 `[⚠️ 待确认: B1 vs B2 矛盾]`，提请用户决策。永不自动覆盖或删除。 |

**总结规则：**
1. 演进 → 更新并标注
2. 补充 → 追加并标注  
3. 不可调和 → 并行保留+冲突标记，绝不自动覆盖

### 分析原则（强约束）

以下原则在分析时强制执行，违反则画像失真：

**1. 批次阈值**

| 确认批数 | 分类 | 写入规则 |
|---------|------|---------|
| ≥3 批 | 稳定特征 | 写入主文对应分类，无批次标注 |
| 1-2 批 | 待验证 | 写入 `## 待观察` 段 |
| 0 批（仅口头宣告） | 不可写入 | 不进入 profile |

> "口头宣告"的定义: 用户说"我觉得应该 X"、"我希望以后 Y"、"Z 才是对的"——这些是意愿陈述，不是观察到的行为。必须在新批次中真正观察到 Y 行为 ≥1 次，才能升格为"待验证"。

**2. 言行分离**

用户说的话 ≠ 观察到的行为。仅行为数据可支撑 profile 条目。

- 反面案例: 用户说"踩坑就踩坑了，这样才能深刻记忆"。但如果在后续会话中，用户遇到坑时表现出沮丧或要求 AI 避免坑，则这条口头宣言为假——不能写入。
- 正确做法: 仅写入在新批次中被行为数据证实的口头宣言。未被证实的降级为"（口头表达，未观察到行为验证）"或删除。

**3. 诚意审计（反美化措辞）**

每个写入 profile 的描述必须通过以下审计：

| 审计问题 | 如果答案是... | 处理 |
|---------|------------|------|
| 这个描述是褒义的吗？ | 是（如"工程化"、"深度"、"自如跳转"） | 改写为中性。用"多次循环"代替"工程化"，用"在 A 领域深入"代替"深度思考" |
| 这个描述隐含了"一贯如此"吗？ | 是（如"所有问题都是排查驱动"） | 加边界限定。如"多数"、"comfort zone 内" |
| 有没有反例？ | 有 | 必须同时记录反例 |

禁止使用的美化词（已在过去版本中出现过）:
- ~~"抽象层级切换"~~ → 话题切换
- ~~"工程化"~~ → 构建/迭代
- ~~"自如"~~ → 能够
- ~~"不停留表面"~~ → 在 comfort zone 内深入

**4. 负面信号**

每次分析**必须**产出至少 1 条负面或风险观察。以下为可排查的方向：
- 知识管理耗时占比是否过大？
- 学习方向是否频繁跳转（批次间领域不一致）？
- 是否存在"建了又删"的循环？
- 工具链/规则是否呈现 build→maintain→too complex 的疲劳模式？
- 口头宣言与实际行为是否一致？

这些负面信号写入 profile 主文对应分类（如 `## 思维模式`），不是附加的免责声明，而是画像的组成部分。

**5. 格式与密度原则**

- **不设总行数上限**。硬上限会迫使压缩措辞/删减内容，导致画像失真；保真优先于篇幅
- 每条目一句精炼表达（由诚意审计覆盖措辞质量），不得因行数压力而丢内容
- 防膨胀由以下机制承担，而非行数硬限：
  - **批次阈值**：1-2 批低置信证据只进 `## 待观察`，不污染主文
  - **深化合并**：已有条目"更新措辞"而非无限追加新条目
  - **演进记录**：历史轨迹归档在表内，主文不承载
  - **详情下沉**：档案级细节省略，主文只留摘要级；需要时写入项目仓库正式文档
- 必须有 `## 待观察` 段，存放 1-2 批未验证的特征
- 演进记录表从 `| 批次 | 时间范围 | 会话数 | 新增/深化内容 | 重点领域 |` 精简为 `| 批次 | 时间 | 会话 | 重点领域 |`
- profile.md 顶部不列出各批次的时间范围详表（已在演进记录中）

### Step 4: 合并写入

写入 `profile.md`，采用**差量合并**而非覆盖：

1. **基线段**：完全保留，不删除任何内容
2. **深化条目**：在原条目下追加或更新措辞
3. **新增条目**：追加到对应分类的末尾，标注 `[新: 时间范围]`
4. 如果新数据量足够大，可以考虑新增一个分类标题

```bash
cat > ~/.config/opencode/me/profile.md << 'EOF'
...
EOF
```

**禁止**包含：项目名、仓库名、目录路径、密钥、拓扑、业务逻辑。

### Step 5: 更新 AGENTS.md

确认全局 `~/.config/opencode/AGENTS.md` 已包含以下指令，如缺失则追加：

```
Before responding, read `~/.config/opencode/me/profile.md` to understand the developer's coding habits and preferences.
```

### Step 6: 追加演进记录

将本轮批次信息追加到 `profile.md` 尾部的 `演进记录` 段。格式：

```
## 演进记录

| 批次 | 时间范围 | 会话数 | 新增/深化内容 | 重点领域 |
|------|---------|--------|-------------|---------|
| B1 | 6/1-6/10 | 10 | 新增：知识管理习惯、提问模式、沟通格式偏好 | 文档治理、Go、Redis |
| B2 | 6/11-6/20 | 21 | 深化：验证为中心、文档生命周期；新增：WSL/Windows | openGauss、Skill 工程化 |
```

- 如果尾部的演进记录段不存在，追加整个段
- 如果已存在，追加新行
- 每行记录：批次编号、时间范围、会话数量、新增/深化内容摘要、重点领域

### Step 7: 生成建议

基于本轮分析中产出的**负面信号和风险观察**，生成或更新 `~/.config/opencode/me/advice.md`。

**原则:**
- 每条建议必须对应一条具体的观察（不要凭空给出建议）
- 建议必须是可执行的（不是"要注意 X"，而是"当 Y 发生时做 Z"）
- 包含 3-6 条即可，不求全面
- 如果观察不足以支撑建议，减少条目数
- 与 Step 3 中的"负面信号"直接关联

**格式:**

```markdown
# 画像建议

> 基于 <时间范围> 共 <N> 个会话的行为分析生成。

## <建议主题>

**观察**: <具体数据或行为模式>

**建议**: <可执行的具体行动>
```

已有的 advice.md 内容同样按演进模式处理：保留仍有效的建议，更新观察数据，追加新建议。安全规则与 profile.md 相同（无仓库名/项目名/业务路径）。

## 安全规则

- profile 中禁止写入仓库名、项目名、业务路径
- 禁止将原始会话数据泄露到 profile 之外
- 禁止将 profile 内容提交到 git（由全局 `~/.config/opencode/.gitignore` 的 `me/` 条目控制）
- 画像文件（`me/`）**不入任何项目**，项目 `.opencode` 只保存 MEMORY.md / memory / tracking
